# OpenVINO coverage report build

The coverage report is generated using Lcov tool and based on profile data generated by GCC.
The generated reports are in HTML form and located in `<openvino_build>/coverage`. The reports are generated for the following components:

1. `inference` - Inference component is a part of OpenVINO Runtime library.
1. `core` - Core component is a part of OpenVINO Runtime library.
1. `low_precision_transformations` - Low Precision transformations is a part of OpenVINO Runtime library.
1. `openvino_transformations` - Common transformations is a part of OpenVINO Runtime library.
1. `snippets` - OpenVINO snippets.
1. OpenVINO open-source plugins:
    - `hetero_plugin` - Heterogeneous plugin.
    - `auto_plugin` - Auto plugin.
    - `proxy_plugin` - Proxy plugin.
    - `auto_batch_plugin` - Auto-batching plugin.
    - `template_plugin` - Template plugin.
    - `intel_gpu_plugin` - GPU plugin.
    - `intel_cpu_plugin` - CPU plugin.
    - `intel_npu_plugin` - Intel® NPU plugin.

## Build with profiling data support

To build coverage report, compile OpenVINO with an additional CMake option `-DENABLE_COVERAGE=ON`:

```bash
$ cmake -DENABLE_COVERAGE=ON .
```

And build OpenVINO as usual.

## Generate coverage report

In order to generate coverage reports, first of all, the tests must be run. Depending on how many tests are run, the better coverage percentage can be achieved. E.g. for `openvino` component, `InferenceEngineUnitTests`, `ieUnitTests`, `ieFuncTests` must be run as well as plugin tests.

```bash
$ ctest -V
```

OpenVINO components define several common groups which allow to run tests for separate component (with ctest argiment `-L GROUP_NAME`):

 - OV - core OpenVINO tests
 - IR_FE - IR frontend tests
 - ONNX_FE - ONNX frontend tests
 - PADDLE_FE - Paddle frontend tests
 - TF_FE - TensorFlow frontend tests
 - TFL_FE - TensorFlow Lite frontend tests
 - CPU - CPU plugin tests
 - GPU - GPU plugin tests
 - AUTO - Auto plugin tests
 - MULTI - Multi-device tests covered by the Auto plugin
 - AUTO_BATCH - Auto-batching plugin tests
 - PROXY - Proxy plugin tests
 - NPUW - Intel® NPU unit tests


After sufficient number of tests are executed, the coverage numbers can be calculated. In order to do this, run:

```bash
$ make ov_coverage
```

The following tree of reports are generated:

```bash
$ find coverage -maxdepth 2 -name index.html
coverage/auto_batch_plugin/index.html
coverage/auto_plugin/index.html

coverage/openvino/index.html
coverage/onnx_frontend/index.html
coverage/ir_frontend/index.html
coverage/low_precision_transformations/index.html
coverage/proxy_plugin/index.html
coverage/template_plugin/index.html

```

## Local Windows NPU coverage experiment

The Windows coverage branch includes experimental PowerShell build/run scripts.
They do not change the CI workflow, upload results, or install coverage tools
automatically. A separate, explicitly invoked installer is available for OpenCppCoverage.
Use PowerShell 7 and an **x64 VS2022 Developer PowerShell** environment, with the
C++ workload, Windows SDK, CMake 3.26+, Ninja, Git and Python 3.11+ on PATH.
VS2022 Professional is sufficient to build; availability of native coverage is
what this experiment is intended to establish. CI uses MSVC toolset 14.42.

From the repository root:

```powershell
pwsh -File scripts/build_windows_npu_coverage.ps1 -Jobs 8
pwsh -File scripts/run_windows_npu_coverage.ps1 -Mode Plain
```

The build uses Ninja Multi-Config, Release, `ENABLE_COVERAGE=ON` and
`ENABLE_PDB_IN_RELEASE=ON`, as in the Windows workflow. It keeps CPU (needed by
NPUW), NPU and IR support, but omits Python/JS bindings, wheels, samples and other
frontends to reduce dependencies. `ENABLE_FUNCTIONAL_TESTS=ON` is required because
NPU and HETERO also configure functional test targets that need the shared test
utilities. This does not select them for execution. Other C++ tests may be built/installed, but only
`ov_npu_unit_tests.exe` is run. There is no shared compiler cache or CI packaging
metadata. Submodules and CMake dependencies require network access; configure
your machine's proxy/CA trust if needed.

Outputs are `build-windows-npu-coverage/package` and
`build-windows-npu-coverage/openvino-npu-coverage.zip` (runtime, tests and PDBs
together). The script refuses to reuse an existing package to avoid stale files;
move it aside before rebuilding, or choose another `-WorkDir`.
The script checks that coverage remains enabled after CMake configuration.
`ENABLE_COVERAGE:INTERNAL=ON` in the cache is not sufficient: it can mean that
CMake saved the requested value while disabling the option in the active scope.
You can unpack the ZIP elsewhere and pass that directory as `-PackageDir`.
Keep the matching source checkout available at its original path for symbol/source
resolution during the first experiment.

### Try standalone VSTest first

With [NuGet CLI](https://learn.microsoft.com/nuget/install-nuget-client-tools)
available, download the complete runner package into an ignored local directory.
Use Microsoft's **Test Adapter for Google Test** component from the VS2022
Installer (Individual components); it is available with Professional:

```powershell
nuget install Microsoft.TestPlatform -Version 18.0.0 -OutputDirectory build-windows-npu-coverage/tools -Source https://api.nuget.org/v3/index.json -NonInteractive

$vstest = "$PWD/build-windows-npu-coverage/tools/Microsoft.TestPlatform.18.0.0/tools/net462/Common7/IDE/Extensions/TestPlatform/vstest.console.exe"
$vs = 'C:\Program Files\Microsoft Visual Studio\2022\Professional'
$adapterDlls = @(Get-ChildItem "$vs\Common7\IDE" -Recurse -File -Filter 'GoogleTestAdapter.TestAdapter.dll' |
    Where-Object { $_.Name -eq 'GoogleTestAdapter.TestAdapter.dll' })
$adapterDlls | Select-Object FullName
if ($adapterDlls.Count -ne 1) { throw 'Locate the installed Microsoft Google Test adapter DLL and set $adapter to its directory.' }
$adapter = $adapterDlls[0].DirectoryName
pwsh -File scripts/run_windows_npu_coverage.ps1 -Mode VSTest -ToolPath $vstest -AdapterPath $adapter
```

This uses native **dynamic** instrumentation by default. Repeat with
`-Instrumentation Static` to compare, if supported by the installed collector.
The standalone runner requires the .NET Framework runtime appropriate to that
package. Keep the entire package, not just its EXE, and use the installed adapter
directory without copying individual DLLs. Do not mix multiple adapter versions.
The standalone NuGet `GoogleTestAdapter 0.18.0` is unsuitable for these tests:
its name parser truncates parameter names containing punctuation such as `[`.
Distinct tests then collide and execution can fail in
`CommandLineGenerator.GetFinalCommandLines` with
`Sequence contains more than one matching element`. Microsoft's adapter uses a
different parser that preserves these characters.

The local VSTest settings select the Microsoft adapter's legacy discovery/execution
path (`UseNewTestExecutionFramework=false`) and disable test source-location lookup
(`ParseSymbolInformation=false`). Do not add `ShowFixtureMethodNode`: the schema
embedded in adapter 1.17.0.38 does not support it, and an unsupported setting can
cause the entire adapter settings section to be discarded in favor of defaults.
Validate settings against the installed adapter's embedded
`GoogleTestAdapterSettings.xsd`, not just the current upstream schema. This is a
workaround for the observed `NewCreateTestcases` /
`Path.GetFullPath` discovery exception, verified with adapter 1.17.0.38.
These settings affect the test adapter only: the coverage collector still uses
PDBs to map native code to source lines. No tests are intentionally filtered out.
A Cobertura attachment from a failed discovery run alone is not evidence that
the tests ran or that their coverage was collected.

### Try Microsoft.CodeCoverage.Console if available

```powershell
$collector = 'C:\path\to\Microsoft.CodeCoverage.Console.exe'
pwsh -File scripts/run_windows_npu_coverage.ps1 -Mode Console -ToolPath $collector -Instrumentation Static
```

This uses the workflow's static native instrumentation approach. `CodeCoverage.exe`
from the NuGet packages is **not** compatible with this command line.

### Try OpenCppCoverage

From a PowerShell terminal **running as administrator**, use:

```powershell
.\scripts\install_windows_opencppcoverage.ps1
```

This downloads the **x64** installer from the official
[OpenCppCoverage 0.9.9.0 release](https://github.com/OpenCppCoverage/OpenCppCoverage/releases/tag/release-0.9.9.0).
It checks a pinned SHA256, installs silently without restarting Windows or closing
running applications, then runs a native-process smoke test under the collector.
OpenCppCoverage 0.9.9.0 returns its generic failure code even for successful
`--help`, so help's exit code is not used as a readiness check. The smoke test
runs Windows `whoami.exe` and checks that the collector exits successfully and
exports XML; it does not establish NPU source coverage. Its diagnostics are kept
in a timestamped `OpenCppCoverage-check-*` directory beside the installer.
The checksum pins
the downloaded release artifact; upstream does not publish a separate checksum.
The installer and timestamped installation log remain under
`build-windows-npu-coverage/tools` (override with `-DownloadDir`).
The default destination is `C:\Program Files\OpenCppCoverage` (override with
`-InstallDir`, and use that same location in `-ToolPath` below).
The helper works with Windows PowerShell 5.1; no NuGet or `pwsh` is needed.
Keep its installed dependencies alongside the executable. The project is archived;
compatibility with this MSVC build must be established by the experiment.

Use the existing package and matching PDBs first, without rebuilding. From the
repository root, in Windows PowerShell 5.1 or PowerShell 7:

```powershell
.\scripts\run_windows_npu_coverage.ps1 `
    -Mode OpenCppCoverage `
    -ToolPath 'C:\Program Files\OpenCppCoverage\OpenCppCoverage.exe'
```

This launches the NPU unit-test EXE directly under OpenCppCoverage's debugger-based
collector. It needs neither VSTest nor a Google Test adapter nor Microsoft's
`covinstrc64.exe`. Do not pass `-Instrumentation Static`: that parameter selects
Microsoft collector modes, not OpenCppCoverage instrumentation.

The script collects both the EXE and NPU plugin DLL, excludes test/third-party
sources, and lets expected C++ exceptions reach the test program's handlers.
It keeps module coverage separate (`--no_aggregate_by_file`) so the shared
validator can require hits from both modules before merging source lines.
It does not enable `--optimized_build`: upstream documents that heuristic as
unnecessary for x64. Release optimization can still affect source-line mapping;
a higher percentage alone does not prove better coverage than VSTest.

Each run retains `tests.xml`, `coverage.cobertura.xml`, `html/index.html`,
`run.log` and the collector's `LastCoverageResults.log` in its results directory.
The root-relative `src\...` PDB paths from the local build are mapped to the
current checkout for source display. Keep that checkout at the build revision.
HTML and XML are raw collector reports; the deduplicated production-only console
summary can differ from their totals. This mode does not upload to Codecov or
normalize the XML for upload.

Every invocation writes to a new directory under `build-windows-npu-coverage/results`
(override with `-ResultsDir`). It retains console logs, generated settings, test
results and coverage diagnostics even when tests fail. Coverage modes request
Cobertura and require covered production NPU lines from both modules. Native stderr is logged as text so
Windows PowerShell 5.1 does not stop the child at its first error message; exit
codes and XML results are still checked. Source inclusion accepts both absolute
paths and root-relative `src/plugins/intel_npu/...` paths: local MSVC builds use
`/d1trimfile`, unlike GitHub Actions builds. Requiring a slash before `src`
silently drops most production code, potentially leaving only generated sources.

The summary merges lines by source path and line number across modules and report
copies, retaining a hit if any copy has one. It counts only NPU production files
present in the checkout containing the script, excluding tests, third-party and
build-generated files. Raw Cobertura remains unchanged and is not ready for Codecov:
the collector can retain inline STL/header entries despite its source filters,
and VSTest can save the same report twice. The summary denominator is the source
lines represented in the report, not all lines in the NPU source tree.

All enabled NPU unit tests are selected, without the workflow's hardware/offline
lane split or device checks. Inherited `GTEST_*` and `OV_DQ_TEST_DEVICE` variables
are cleared for the run; hardware roundtrip is not opted into. An NPU/driver is not
a prerequisite, although individual tests may fail. Failures remain visible and
produce a nonzero script exit after retaining available reports.

Native dynamic coverage has been verified with VS2022 Professional (MSVC 14.42),
Microsoft.TestPlatform 18.0.0, Microsoft Google Test adapter 1.17.0.38 and Windows
PowerShell 5.1: all 3090 enabled tests passed and both the test EXE and plugin DLL
contributed coverage. This does not validate the static/Console alternatives or
other tool versions. These remain local investigation helpers; start with `Plain`
to separate runtime/test failures from adapter/collector failures.
